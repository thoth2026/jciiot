# JCIIOT 2026 工业分拣任务 技术报告

**成绩：100 / 100**（L1 10/10、L2 15/15、L3 20/20、L4 25/25、L5 30/30，五关全部零碰撞）

---

## 一、技术描述

### 1.1 整体架构

系统沿用赛方提供的三层结构，我们的工作集中在中间的技能层和底层的抓取实现：

```
LLM 规划器  ──►  技能层 move / pick_up / place_down  ──►  robosuite + MuJoCo
（拆解任务）      （本次工作的主体）                      （物理仿真）
```

LLM 只负责把"把物料从 A 搬到 B"拆成 `move → pick_up → move → place_down` 的步骤序列，
不参与任何几何计算。所有位姿、路径、抓取点都由技能层从场景语义地图和物体的
grasp site 直接算出，因此结果是确定性的、可复现的，不依赖模型输出的稳定性。

### 1.2 抓取：从行为克隆策略改为几何抓取点 + 严格物理校验

**这是我们改动最大的部分。**

赛方基线用的是一个行为克隆（BC）策略（`model_epoch_150.pth`，robomimic 训练的
GPT backbone）来驱动机械臂完成抓取。我们在早期测试中发现它在本场景的成功率不稳定，
且失败时机械臂会直接伸进桌子里，既抓不到又产生碰撞判罚。

我们把抓取重写为**几何抓取点驱动 + 严格物理校验**：

1. **目标点来自场景本身。** 每个物料在 MuJoCo 模型里都定义了
   `<object>_left_grasp_site` / `_right_grasp_site` / `_center_site`。我们直接读取这三个点，
   按工位配置的模式（`x_front_edge` 从 +X 面接近 / `negative_y_edge` 从 −Y 面接近）
   推算出两只夹爪各自的目标位姿。
2. **底盘先摆正。** 抓取前把底盘对准工位法向（`approach_yaw`），再沿该方向退到
   `approach_m` 距离。这一步保证两只手对称地分布在机器人前向轴两侧——因为目标点是按
   世界坐标算的，底盘一歪，远端那只手就够不着。
3. **闭环下降。** 用 OSC 增量控制把两手驱到目标点，每步重新计算误差，直到两只手
   都进入容差（`settle_tolerance`）才闭合，而不是固定步数后硬闭。
4. **严格校验。** 闭合后检查夹爪与物体的接触对，再抬升并保持 80 步，确认物体
   跟着上来（`object_lift_delta`）。校验不过就判定抓取失败，绝不"假装抓到了"。

搬运阶段使用赛方 `robosuite/environments/factory_sorting/transport_attachment.py`
提供的接口——这与赛方 `grasp_object_physics` 在校验抓取和抬升之后调用的是同一个 helper。

### 1.3 导航

- 基于场景语义地图的占据栅格做 A\* 规划，栅格已按机器人半径 0.35 m + 余量 0.10 m 膨胀。
- A\* 只保证栅格路径无碰，路径简化后实际直线段仍可能切角，因此增加了一步
  **直线段重采样检查**，逐点验证机器人真正要走的那条直线。
- 少数工位（L2 的 `input_6`、L3 的 `aux_input_1`、L4 的 `input_2`）默认接近点位于
  物料的另一侧或过于贴近桌面，我们为这些工位配置了显式的接近路径和停靠位姿。

### 1.4 第三方库

| 组件 | 用途 |
|---|---|
| MuJoCo | 物理仿真（赛方环境） |
| robosuite | 机器人与场景建模、控制器（赛方环境） |
| robomimic | BC 策略加载（保留为兜底路径，主流程不使用） |
| NumPy | 全部几何计算 |
| Streamlit | 赛方提供的运行界面 |

未引入任何额外的第三方规划/抓取库，所有算法均为自行实现。

## 二、新颖性说明

### 2.1 L3：先推后抓——用非抓取式操作创造抓取条件

L3 的蓝色料箱又高又靠里，两侧被相邻料箱夹住，从任何一个方向直接下爪，夹爪都只能
碰到箱壁外侧，无法形成有效包络。**直接抓是抓不到的。**

我们的做法是把这一关拆成两段动作：

1. **推。** 机器人先开到桌子的一侧，双臂从料箱下缘伸入，把箱子沿 +Y 方向推出约
   0.15 m，使其上缘从相邻料箱之间露出来。
2. **绕。** 保持箱子不动，机器人绕过桌子的另一端，走到桌子对面。
3. **抓。** 从相反方向接近，两只夹爪从露出来的上缘兜进去，抬升。

这类"先用非抓取式操作（推、拨）改变物体位姿，再执行抓取"的思路，在文献中被称为
**pre-grasp manipulation** 或 **push-grasping**，代表性工作有 Dogar 与 Srinivasa 的
push-grasping 框架（RSS 2011），以及 Zeng 等人用自监督强化学习让推与抓协同的工作
（IROS 2018）。这些工作大多在桌面小物体、固定机械臂的设定下验证。

我们的差异在于：**推和抓之间隔着一次完整的移动基座导航**。机器人推完之后要绕行
约 6 米走到桌子另一侧，这带来了一个上述工作不会遇到的问题——**推出来的位姿在这段
时间里未必还成立**。我们把抓取目标点改为在导航结束、机械臂收起之后**按料箱的实时
位姿重新解算**，而不是沿用推完那一刻的坐标。这一点是这关能做成的关键。

### 2.2 一个反直觉的发现：位姿漂移的来源是机器人自己

调试过程中我们观察到料箱在推完之后会"漂回"原位（y 从 8.622 退回 8.48），最初判断是
物理松弛。逐帧对齐料箱位移与底盘位姿后发现完全不是：

| 帧 | 料箱 y | 底盘 y | |
|---|---|---|---|
| 895 | 8.622 | 7.723 | 推完，底盘静止 |
| 1148 | 8.591 | 9.335 | 底盘开始最后的垂直接近 |
| 1151 | 8.524 | 9.230 | 4 帧内退了 67 mm，**与底盘下降完全同步** |

料箱只在底盘移动时移动。**是机器人在最后接近阶段用手臂把自己刚推好的箱子又撞回去了。**

这个发现改变了整个方案的走向。我们据此把机械臂在整个接近段收拢到底盘正上方，
料箱随即稳定在推后位姿不再移动，抓取一次成功。

### 2.3 按碰撞代理的几何特征设计规避动作

判罚碰撞只统计 `scene_aabb_proxy_*` 代理几何体。我们量化了两侧的实际尺寸：

- 桌面代理 `side_table_pos_y_2` 的**高度范围只到 z ≤ 0.90 m**；
- 机器人躯干碰撞盒在底盘系下为 x ∈ [−0.227, 0.273]、y ∈ [−0.25, 0.25]，
  **原地旋转时扫过的角半径是 0.370 m**。

由此得到两条可直接计算的规避规则：

1. **把手抬到 z = 1.30 m** 就完全脱离桌面代理的高度区间——这一条清掉了 74 次碰撞中的 49 次；
2. **原地转身必须离桌面 ≥ 0.370 m**。原方案转身时底盘在 y = 7.723，桌面 −Y 面在 8.055，
   只剩 0.332 m，**差 38 mm**。改为先后退 0.55 m 转身、再开回原落点，清掉 13 次。

第二条有个实现上的坑值得记录：**"转身会把底盘带到哪"不能靠正向运动学预测**。
偏航关节在底盘中心后方 0.21 m，自由空间中转 180° 会把中心带出 0.42 m；但原方案里
桌子挡住了它，实际只走了 0.26 m。按预测值开回去会把底盘塞进桌子 0.16 m（实测产生
1855 次碰撞）。正确做法是用实测落点。

## 三、结果与分析

### 3.1 定量结果

五关均以赛方默认配置（不设任何环境变量）端到端跑通，并用一个逐行复刻 `app.py`
计分逻辑的脚本独立复算：

| 关卡 | 抓取+离开工位 | 放置到目标台 | 碰撞判罚 | 总分 | 落点距工位中心 |
|---|---|---|---|---|---|
| L1 | 5/5 | 5/5 | 0 | **10/10** | 0.151 m |
| L2 | 7/7 | 8/8 | 0 | **15/15** | 0.287 m |
| L3 | 10/10 | 10/10 | 0 | **20/20** | 0.100 m |
| L4 | 12/12 | 13/13 | 0 | **25/25** | 0.323 m |
| L5 | 15/15 | 15/15 | 0 | **30/30** | 0.652 / 0.716 / 0.179 m |
| | | | | **100/100** | |

L5 需要往返三趟分别搬运三个料箱，上表为三个料箱的合计。

### 3.2 关键改进的量化贡献

| 改动 | 效果 |
|---|---|
| L3 接近段收拢机械臂 + 转身避让 | 判罚碰撞 74 → **0**，落点 0.555 m → **0.100 m** |
| L5 重复取件的物体选择与站位摆正 | 10/30 → **30/30** |
| 搬运步长 4 mm → 20 mm（附着搬运下安全） | L5 单次运行 ~1500 s → **546 s**，碰撞仍为 0 |

### 3.3 优势

- **确定性。** 抓取点来自场景模型，路径来自栅格规划，不含随机采样，重复运行结果一致。
- **失败可见。** 严格物理校验意味着抓取失败会立即报错并中止，不会带着"以为抓到了"的
  状态继续往下走。
- **碰撞规避是算出来的，不是试出来的。** 2.3 节的两条规则直接来自代理几何体的尺寸，
  可以在不跑仿真的情况下预先判断某个位姿是否安全。

### 3.4 局限性

我们认为有必要如实说明以下几点：

1. **移动底盘是通过直接写入 qpos 驱动的，不是由其执行器驱动的。** 这是本环境的固有
   约束：底盘自重约 77.8 kg 压在地面（摩擦系数 1，法向力约 763 N），加上移动关节
   `frictionloss = 250`，而底盘执行器上限只有 ±600 N。我们实测满速指令下底盘 200 步
   只移动了 1 mm。赛方基线的导航脚本同样采用写入 qpos 的方式。相应地，搬运阶段
   使用赛方 `transport_attachment` 保持物体与底盘的相对位姿。

2. **L3 的抓取是"兜住"而非"力封闭夹持"。** 该料箱较高，两只夹爪实际是从上缘两侧
   兜入并托起，接触点分布在箱体的底面与侧壁。校验方式是接触 + 抬升位移，而非力封闭
   判据。这个抓取对位姿较敏感，这也是我们必须让料箱在抓取前完全静止的原因。

3. **部分工位的接近位姿是针对本场景标定的**，例如 L4 的停靠点 (−9.849, 6.303) 是躯干
   碰撞盒在不触碰 `input_2` 代理的前提下能达到的最近位置。换到布局不同的新场景需要
   重新标定。这是以确定性换取的代价。

4. **L5 三个料箱被放置在同一位置附近**，最远的一个距工位中心 0.716 m，虽在 0.80 m
   判定阈值内，但余量不大。放置点目前是机器人停靠位，没有为多次放置做散开处理。

## 四、复现方式

```bash
cd JCIIOT
streamlit run app.py
```

全部改进均为默认配置，无需设置任何环境变量。

不经过 LLM 规划器、直接运行单关（用于验证）：

```bash
python src/robot_agent/workflows/fixed_task_sequence.py --task-index 2
```

`--task-index` 取值 0–4 分别对应 L1–L5。

调试过程中的完整实验记录（含所有失败尝试及其原因）见 `JCIIOT/TUNING_LOG.md`。
